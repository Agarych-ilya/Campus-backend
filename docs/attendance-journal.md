# CampusApp · журнал посещаемости старосты

## Что реализовано

В разделе расписания Flutter, внутри конкретной пары, открывается
«Учебный журнал · посещаемость». Базовый принцип взят из старого
Telegram-бота: студент сообщает «Я присутствую», староста подтверждает
заявку и вручную проверяет отсутствующих.

**Это журнал CampusApp, не прямое изменение официального БАРС.**
Предпросмотр для БАРС доступен после закрытия журнала. Автоматической
записи пропусков в БАРС **пока нет**: предоставленный образец HTML
содержит только родительскую страницу журнала и динамические
`_PartialList...` секции, но не подтверждённые текущие формы,
anti-CSRF-условия и действующее API записи. Selenium/XPath из бота
использовать без повторного аудита нельзя.

## Доступ и идентификация

Студент повторно не авторизуется: используется существующая
БАРС-сессия CampusApp, уже проверенная маршрутом
`POST /services/listings/bars-login`. Отдельный пароль старосты не нужен.

Группа и непрозрачный персональный ключ всегда получаются из
подтверждённой сервером сессии БАРС. Имя отображения студент вводит
сам — оно ещё не подтверждает официальную личность из БАРС.

Роль старосты теперь определяется на backend автоматически, когда
существующая БАРС-сессия подтверждает студента, а защищённые страницы
`Учебные группы → группа → Староста` связывают его с аккаунтом
авторизованного пользователя БАРС. Ключ группы проверяется на сервере;
флаг `isStarosta` из Flutter **никогда не принимается**.

Для старой разметки БАРС остаётся резервный способ выдачи прав по
проверенной зачётке — серверная настройка (не обязательная):

```dotenv
CAMPUS_STAROSTA_GROUP_BOOKS=А-03-23=НОМЕР_ЗАЧЁТКИ
```

Для нескольких групп используйте `;` между парами `ГРУППА=ЗАЧЁТКА`.
Пользователи со старой сессией могут нажать **«Проверить права
старосты»** в журнале для повторной проверки доступной сессии БАРС,
без удаления профиля и повторного ввода ФИО. Если HTML страницы
«Староста» изменён и проверка не может быть выполнена, права не
выдаются автоматически.

Настройте `SESSION_SECRET` не короче 32 символов. Модуль использует
существующие `campus.sid` и `X-Listing-CSRF`; записи без корректного
CSRF-заголовка отклоняются. Не храните в конфигурации пароли БАРС,
cookie, ФИО всей группы или Telegram-токены.

## Как теперь работает журнал старосты

Список студентов **не вводится вручную**. Староста открывает учебный
журнал выбранной пары в CampusApp и нажимает **«Загрузить группу из БАРС»**.
Приложение автоматически проходит `Учебные группы → своя группа (А-03-23)
→ Студенты`, читает таблицу по заголовкам `ФИО` и
`Статус обучения` и автоматически увеличивает число отображаемых
строк, если БАРС разбивает список на страницы.

Старосте остаётся **проверить ФИО и подтвердить импорт**.
Если университетский сайт поменяет структуру, доступен запасной
ручной режим. Неизвестные или частично загруженные таблицы не
сохраняются в CampusApp.

Приложение читает только видимую таблицу на
`https://bars.mpei.ru/bars_web/...`, сравнивает отображаемую группу с
подтверждённой группой сессии и показывает ФИО на проверку. После
подтверждения весь список импортируется в защищённую MySQL-таблицу
`campus_attendance_roster`. Повторный импорт обновляет список.
Идентификаторы студентов для CampusApp создаются через HMAC и не
раскрывают исходные идентификаторы BARS; имена доступны только
старосте этой группы.

**Ограничение подтверждения:** таблицу извлекает WebView клиента,
поэтому backend не может независимо подтвердить каждую импортированную
запись. До официальной синхронизации староста обязан сверить полноту
содержимого. Если вкладка `Студенты` имеет другую HTML-разметку,
приложение сообщает, что таблица не распознана, и **не создаёт
выдуманных студентов**.

Когда группа загружена, староста открывает журнал пары:
- весь список отображается сразу;
- староста ставит галочки **только напротив отсутствующих**;
- остальные становятся `present` лишь после явного подтверждения
  итогового экрана;
- кнопка **«Сохранить посещаемость»** фиксирует итог для всех членов
  группы и закрывает журнал одной транзакцией;
- сервер сравнивает набор студентов с последней просмотренной версией
  и не принимает устаревший или подменённый набор;
- состав группы сохраняется отдельно для конкретной пары, чтобы
  следующий импорт не менял уже закрытые журналы.

## Буква «Н» в расписании CampusApp

После того как староста подтверждает отсутствующих и закрывает журнал,
в расписании **только самого отсутствовавшего студента** возле
соответствующей пары появляется компактная красная буква **«Н»**.
Отметки других студентов клиенту не передаются. Учитываются дата,
время, предмет, тип занятия и аудитория. Для незакрытого журнала,
отсутствия однозначного сопоставления с аккаунтом БАРС либо просмотра
чужой учебной группы метка не показывается.

Сопоставление использует только подтверждённые сервером данные
пользователя из БАРС. При импорте таблицы студентов приложение считывает
также университетскую почту (если она есть). Backend хранит **HMAC**
идентификатора студента и университетского логина, а не адрес электронной
почты, raw ID или пароль. Старая версия списка, созданная без этой
привязки, требует **одного обновления списка из БАРС**; студенту может
понадобиться обновить вход в БАРС для получения метки.

`GET /services/attendance/my-absences?from=YYYY-MM-DD&to=YYYY-MM-DD`
возвращает только пропуски **текущего авторизованного студента** за
период не более 43 календарных дней. Записи получаются исключительно
из закрытых журналов и проверенного снимка состава группы.

Официальный БАРС **пока не изменяется**. Экспорт
`bars-preview` даёт сверочный список отсутствовавших, но не нажимает
кнопки в веб-журнале и не подставляет XPath из старого Telegram-бота.

Ключи сессии, cookies и пароли БАРС не сохраняются в таблице списка.
Роль старосты проверяется по защищённой странице БАРС.
`CAMPUS_STAROSTA_GROUP_BOOKS=ГРУППА=ЗАЧЁТКА` допускается как
резервный режим. Скриншот с ФИО сам по себе не заменяет
серверную проверку права редактирования.

## API

| Метод | Путь | Кто |
|---|---|---|
| GET | `/services/attendance/session` | информация о сессии |
| GET | `/services/attendance/roster` | текущий импортированный список, только староста |
| POST | `/services/attendance/roster/import` | импорт всей группы, только староста |
| POST | `/services/attendance/lessons/:id/absences` | выбрать отсутствующих и закрыть журнал |

| POST | `/services/attendance/register` | студент |
| GET | `/services/attendance/lessons?date=YYYY-MM-DD` | своя группа |
| POST | `/services/attendance/lessons` | староста |
| GET | `/services/attendance/lessons/:id` | своя группа (ограниченный ответ) |
| POST | `/services/attendance/lessons/:id/check-in` | студент |
| PATCH | `/services/attendance/lessons/:id/decision` | староста |
| POST | `/services/attendance/lessons/:id/close` | староста |
| GET | `/services/attendance/lessons/:id/bars-preview` | староста |

Тело `POST /lessons`:

```json
{
  "date": "2026-11-14",
  "time": "10:00–11:30",
  "subject": "Теория управления",
  "type": "Лекция",
  "room": "В-308"
}
```

Данные занятия — из существующего расписания, а не из произвольного
ввода пользователя. Тело решения старосты:

```json
{"ownerKey":"<непрозрачный_ключ_студента>","status":"present"}
```

Поддерживаемые итоговые значения: `present`, `absent`,
`excused`; `rejected` отклоняет заявку, но закрытие журнала требует
итогового решения для каждого студента.

## Если журнал показывает ошибку сессии БАРС

Внутри журнала есть кнопки **«Повторить проверку»** и
**«Обновить вход в БАРС»**. Вторая открывает встроенный WebView для
повторной авторизации и после неё возвращает к той же паре, не удаляя
локально сохранённый профиль. При запуске CampusApp может использовать
кэшированный профиль, даже если cookie БАРС уже истекли.
Проверка занимает время: backend последовательно обращается к двум
защищённым страницам БАРС, поэтому Flutter ждёт до 35 секунд
для авторизационного обмена. Не нужно вводить пароль повторно
при каждом сетевом сбое.

- `БАРС не подтвердил сессию (список студентов, HTTP 302)`
  или аналогичная ошибка с этапом `профиль студента` — БАРС вернул
  редирект или HTTP 401/403. Воспользуйся «Обновить вход в БАРС».
  Сами этап и HTTP-код безопасно показать разработчику; адрес редиректа,
  пароль, токены и cookies передавать нельзя.
- `Не удалось связаться с БАРС для проверки сессии` — сервер БАРС
  не ответил, возникла сетевая ошибка либо HTTP 429/5xx.
  Это не доказательство истёкшей сессии: сначала проверь сеть между
  backend и `https://bars.mpei.ru`, затем повтори проверку.
- `БАРС не подтвердил единственный профиль студента` — на защищённой
  странице нет ровно одной проверенной строки студента; требуется
  анализ текущей разметки и подтверждение привязки к БАРС.

Backend выводит безопасную диагностику
`BARS verification: request-failed stage=... status=... code=...`.
Логи **не** содержат cookies, имён, зачёток и HTML. Не публикуйте
скриншоты cookie или Request Headers из DevTools.

## Что нужно для следующего этапа — официального БАРС

Чтобы записывать в государственную/университетскую систему учёта,
потребуется подтвердить права старосты на редактирование конкретного
журнала в БАРС, получить точную актуальную структуру формы занятия и
механизм защиты записи, а также сопоставить список студентов БАРС и
CampusApp по удостоверенной личности. Затем добавляется **двухэтапная
синхронизация**: предпросмотр изменений → явное подтверждение →
запись → проверка результата → журнал аудита. Нельзя слепо нажимать
«Отметить всех» или перенести хрупкие XPath из старого Selenium-кода.

Тестовая команда:

```powershell
npm run build
npm test -- --runInBand attendance.service.spec.ts
```
